# randevu 백엔드 개선 기록 (2026년 9월)

서비스를 운영 관점에서 다시 점검하며 의심 가는 지점을 목록(점검 항목 **R-1 ~ R-10**)으로 만들고,
항목마다 실제로 문제인지 먼저 재현·확인한 뒤 고쳤다. 고치는 과정에서 새로 드러난 문제(**N-1 ~ N-6**)도 함께 고쳤고,
마지막으로 부하 테스트를 돌려 병목을 찾고 개선했다(**P-1 ~ P-3**, 7장).
항목마다 무엇이 문제였는지, 왜 그 방법을 골랐는지, 어떻게 고쳤는지, 무엇으로 확인했는지를 남긴다.

- 대상: `main` `60c480a` 이후 커밋
- 테스트: 7개 스위트 38개 → **20개 스위트 123개** (`npm test`)
- 측정 환경: Apple M2(8코어) · 16GB, macOS, 로컬 PostgreSQL 17.4, Node 26, 역 879개 · 간선 1,998개 · 환승 374개 · 캐시 447,097행
  - 측정값은 이 환경 기준이라 절대값보다 **전후 비율**을 보는 것이 맞다.
  - DB 측정은 운영·개발 DB가 아닌 별도 검증용 DB(지하철 공개 데이터 테이블만 복사)에서 했다.

## 1. 이동시간 캐시 재생성

### 1-1. 최적화 코드 반영과 단계별 측정 (R-3)

**문제**
로컬에서만 작업하던 최적화 코드(`insert()` 청크 적재, CSR 그래프, Dial 버킷 큐)가 저장소에 반영되지 않아,
저장소만 보면 개선 전 코드가 보였다. 개선 효과도 전체 시간만 있고 단계별로 나뉘어 있지 않았다.

**판단**
"적재 개선"과 "탐색 개선"을 다른 커밋으로 나눠 각각의 효과가 드러나게 했다. 첫 커밋에는 정확성 테스트 7개를
먼저 넣고, 원래 다익스트라에서도 이 테스트가 통과하는 것을 확인한 뒤 탐색부를 바꿨다.

**측정** (같은 검증용 DB, 전체 재생성)

| 단계 | 전체 재생성 | 탐색만 (879개 출발역) |
|---|---|---|
| 원본: `save(rows, { chunk: 1000 })` + `sort()`/`shift()` 다익스트라 | 76.4초 | 0.37초 |
| `3adda56` `insert()` 5,000행 청크 | 6.4초 | 0.39초 |
| `5bc7add` + CSR 그래프 · Dial 버킷 큐 | 6.35초 | **0.023초** |
| `1ff781e` + 한 트랜잭션 · `unnest` 적재 (1-3) | 5.1 ~ 6.1초 | 0.023초 |

- 전체 시간의 대부분은 적재였다. 탐색부 개선(약 16배)은 전체 시간에 거의 영향을 주지 않는다.
  탐색부 개선의 의미는 "요청 시점 경로 계산을 도입할 때 대비"에 있다.
- `save()`가 느린 이유 확인: TypeORM `EntityPersistExecutor`는 `chunk`로 엔티티를 나누고, 청크마다 `SubjectDatabaseEntityLoader`가
  `whereInIds(allIds)` 한 번으로 기존 행을 조회한다(`node_modules/typeorm/persistence/*` 확인).
  "행마다 조회"가 아니라 "1,000행 청크마다 OR 조건 1,000개짜리 SELECT 한 번 + 엔티티별 변경 감지"가 정확하다.

### 1-2. 재생성 API 인증 (R-1)

**문제**
`POST /stations/travel-time-cache/rebuild`에 가드가 없어 주소만 알면 누구나 캐시를 비우고 다시 채우게 할 수 있었다.
반복 호출하면 사실상 서비스 거부다.

**판단**
실제 문제다. 사용자 인증(JWT)은 "누구인지"를 확인할 뿐 "운영자인지"를 구분하지 못하므로 별도 관리자 인증이 필요하다.

**방법과 이유**
- `AdminApiKeyGuard`(`src/auth/admin-api-key.guard.ts`): `x-admin-key` 헤더가 환경변수 `ADMIN_API_KEY`와 같을 때만 통과한다.
  - 키가 없거나 32자 미만이면 관리 API를 **아예 열지 않는다(fail-closed, 403)**. 설정 누락이 곧 "누구나 호출 가능"이 되면 안 되기 때문이다.
  - 비교는 양쪽을 SHA-256으로 바꾼 뒤 `timingSafeEqual`로 한다. 길이가 다르면 `timingSafeEqual`이 바로 예외를 던져 길이가 새어 나가므로, 같은 길이의 해시로 맞춘다.
- 사용자 역할(Role) 체계를 새로 만드는 대신 API 키를 택했다. 관리 기능이 이것 하나라 역할 모델, 관리자 계정 관리 비용이 이득보다 크다.
- HTTP를 아예 거치지 않는 방법도 마련했다(1-4의 CLI). 평소에는 CLI를 쓰고, HTTP는 키가 있을 때만 열린다.

**검증**
가드 단위 테스트 5개, Nest + supertest로 실제 라우트를 띄워 "키 없으면 401이고 재생성이 실행되지 않음"을 확인했다.
빌드한 앱을 띄워서도 키 없음·틀린 키 → 401을 확인했다.

### 1-3. 재생성 중 추천 공백 제거와 동시 실행 방지 (R-2, N-1)

**문제**
재생성은 `TRUNCATE` 후 청크마다 자동 커밋으로 채웠다. 그 사이 역 추천은 빈 캐시나 일부만 찬 캐시를 읽었다.
도중에 프로세스가 죽으면 다음 재생성 전까지 캐시가 일부만 남는다. 동시에 두 번 실행하는 것도 막지 못했다.

**판단**
실제로 재현했다. 재생성 중 4개 연결로 역 추천 쿼리를 계속 보냈을 때:

| | 읽기 횟수 | 빈 결과 | 일부만 찬 결과 |
|---|---|---|---|
| 수정 전 (TRUNCATE + 청크 자동 커밋) | 221,595 | **97,769 (44%)** | 211 |
| 수정 후 (한 트랜잭션) | 190,024 | **0** | **0** |

**선택지와 측정** (서버 쪽 SQL만 측정)

| 방식 | 재생성 중 읽기 | 측정 | 판단 |
|---|---|---|---|
| A. 한 트랜잭션에서 `DELETE` 후 `INSERT` | 이전 데이터가 보임(MVCC) | DELETE 0.2~0.35초 + INSERT 3.8초 | **채택** |
| B. 한 트랜잭션에서 `TRUNCATE` 후 `INSERT` | 커밋까지 읽기 대기(ACCESS EXCLUSIVE) | - | 추천 요청이 수 초 멈춤 |
| C. 제약 없는 스테이징 테이블에 적재 후 이름 교체 | 이전 데이터가 보임 | 적재 0.44초 + PK·인덱스·FK 0.33초 | 빠르지만 보류 |

C가 약 5배 빠르지만 A를 골랐다.
- 재생성은 역·노선 데이터가 바뀔 때만 하는 드문 관리 작업이고, 사용자에게 중요한 것은 "재생성 중에도 추천이 정상인가"다. A로 이미 공백 0을 달성한다.
- C는 테이블 교체 시 PK·인덱스·FK 이름을 원래 이름으로 되돌려야 한다. 그렇지 않으면 TypeORM의 이름 규칙과 어긋나 이후 스키마 비교가 틀어진다. DDL·카탈로그 처리가 늘어 실패 경로가 많아진다.
- A의 대가는 지운 44.7만 행만큼의 dead tuple이다. autovacuum이 정리하고, 측정상 테이블이 49MB → 68MB로 늘었다가 VACUUM 후 돌아왔다.

**구현** (`src/stations/stations.service.ts`)
1. `pg_try_advisory_xact_lock`으로 잠근다. 이미 다른 재생성이 잡고 있으면 바로 **409**를 던진다.
   트랜잭션 단위 락이라 커밋·롤백 시 자동으로 풀리고, 프로세스가 죽어도 남지 않으며, 인스턴스가 여러 대여도 DB 기준으로 막는다.
2. `DELETE`로 지운다(`TRUNCATE`는 읽기를 막으므로 쓰지 않는다).
3. 행을 열별 배열 3개로 모아 `INSERT … SELECT * FROM unnest($1::int[], $2::int[], $3::int[])`로 5만 행씩 넣는다.
   바인딩 파라미터가 행 수와 무관하게 3개라, 1만 5천 개 파라미터짜리 다중 VALUES보다 파싱 비용이 작다.
4. 같은 트랜잭션에서 `ANALYZE`해 커밋과 동시에 플래너 통계도 새 데이터 기준이 되게 한다.

**N-1 (추가 발견) 지역 재생성의 비대칭**
기존 지역 재생성은 "출발역 **또는** 도착역이 그 지역"인 행을 지우고, "출발역 **과** 도착역이 모두 그 지역"인 행만 다시 넣었다.
지역 사이가 연결된 노선이 생기면 지역 간 행이 지워진 채 돌아오지 않는다. 지금은 지역별 노선망이 분리돼 있어 드러나지 않았을 뿐이다.
"그 지역에서 출발하는 행을 지우고, 같은 출발역에 대해 전체 재생성과 똑같은 행을 넣는다"로 정의를 바꿨다.

**검증**
- 단위 테스트: 잠금 → DELETE → INSERT → ANALYZE 순서, TRUNCATE 미사용, 잠금 실패 시 409 + 쓰기 없음, 지역 재생성 결과가 전체 재생성의 해당 출발역 행과 같음.
- 실제 DB: 동시에 두 번 호출 → 하나는 409, 하나는 성공, 행 수 447,097 유지(빌드한 앱에 HTTP로도 확인).
- 전체 결과를 원본 알고리즘 결과와 대조 → 차이 0건(1-4). 서울·부산 지역 재생성 후에도 차이 0건.

### 1-4. 재생성 CLI와 결과 검증 SQL (R-1, R-4)

  - 앱과 같은 DB 설정(`src/database/typeorm-options.ts`)을 쓰고, 데이터만 다루므로 스키마 동기화·마이그레이션은 끈다.

## 2. 외부 API 호출

### 2-1. 스케줄러가 동시 실행 상한을 넘는 문제 (R-5 문제 1, N-2)

**문제**
`releaseSlot()`이 카운터를 먼저 줄이고 대기자를 깨웠다. 깨운 대기자는 다음 microtask에서야 실행되므로,
그 사이 같은 tick에 들어온 새 요청이 빈 슬롯을 가로챘고 대기자도 다시 확인 없이 실행됐다.

**판단**
원본 모듈로 그대로 재현했다. 4개 실행 + 1개 대기 상태에서 하나가 끝나는 순간 새 요청을 넣으면 **동시 실행 5개**(상한 4)가 된다.

**N-2 (추가 발견) 최소 간격 계산 오류**
`lastDispatchAt = max(now, lastDispatchAt) + 80`과 `wait = lastDispatchAt + 80 - now`를 함께 써서,
쉬고 난 뒤 두 번째 요청이 80ms가 아닌 160ms를 기다렸다(시작 시각 1000 → 1160 → 1240).
상한을 어기는 방향은 아니지만 불필요한 지연이다.

**방법** (`src/places/request-scheduler.ts`)
- 작업이 끝나면 카운터를 줄이지 않고 **슬롯을 대기자에게 그대로 넘긴다**. 대기자가 없을 때만 줄인다.
- "다음 작업이 시작할 수 있는 시각"을 예약해 순서대로 민다(1000 → 1080 → 1160).
- 대기열에서 10초 넘게 기다린 작업은 실패시킨다. 그만큼 기다려야 한다면 이미 응답이 늦은 것이므로, 부분 결과로 응답하는 편이 낫다.
- 전역 변수 대신 클래스로 바꿔 테스트에서 독립된 인스턴스를 만들 수 있게 했다.

**검증**
barging 상황을 그대로 만든 테스트(최대 동시 실행 4, 먼저 기다린 작업이 먼저 실행), 가짜 타이머로 시작 시각 검증, 대기 시간 초과, 실패 시 슬롯 반납.

### 2-2. 타임아웃, 재시도, 이중 감속 (R-5 문제 4·5·6)

**판단과 방법**
- 타임아웃: `fetch`에 `AbortSignal.timeout`을 붙였다. 네이버·카카오 3초, 소셜 로그인 5초.
  응답이 멈춘 요청이 스케줄러 슬롯을 붙잡으면 슬롯 4개가 모두 막혀 모든 사용자의 장소 검색이 멈추기 때문이다.
- 재시도: 429에서만 최대 2번 재시도한다. `Retry-After`가 있으면 따르고(2초를 넘으면 기다리지 않고 실패), 없으면 지수 백오프에 지터를 섞는다.
  고정 지연은 같은 순간 429를 받은 요청들이 같은 순간 다시 몰리게 한다. 타임아웃·5xx는 느린 상대에 부하만 더하므로 재시도하지 않는다.
- 두 네이버 클라이언트에 복붙돼 있던 재시도 코드를 `src/places/naver-search-request.ts` 하나로 합쳤다.
- 이중 감속 제거: 요청마다 4개씩 묶어 묶음 사이 150ms를 쉬던 부분을 없애고, "요청 하나당 동시 4개"의 슬라이딩 윈도로 바꿨다.
  간격과 전역 동시성은 스케줄러가 맡는다. 동시 4개 제한은 남겨서, 요청 하나가 대기열을 독차지하지 않게 했다.

### 2-3. 채택하지 않은 제안 (R-5 수정 3·4)

- **역 × 카테고리 장소 목록을 배치로 미리 수집**: 지금 데이터로는 맞지 않는다. 역 879개 × 타입 3개 × 검색어 약 14개 ≈ 3만 7천 회로,
  네이버 검색 API 하루 한도(25,000회)를 한 번 수집에 넘는다. 인기 역(가중치 A·B)만 미리 채우는 방식은 검토할 만하다.
- **Redis 토큰 버킷**: 지금은 인스턴스가 한 대라 필요 없다. 스케줄러 주석에 "인스턴스를 늘리면 공유 저장소로 옮겨야 한다"를 남겼다.
- 동시 사용자 조건의 측정은 실제 네이버 API를 대량 호출할 수 없어, 네이버 스텁으로 호출 패턴과 응답 시간을 측정했다(7-4).

### 2-4. 인메모리 캐시 크기 제한과 중복 호출 방지 (R-6)

**문제**
캐시가 일반 `Map`이라 같은 키로 다시 조회될 때만 만료 항목을 지웠다. 검색어는 사용자가 마음대로 입력하므로 키 종류에 끝이 없다(메모리 누수).
캐시가 비는 순간 같은 키 요청이 몰리면 모두 외부 API를 호출했다(cache stampede).

**방법** (`src/common/ttl-lru-cache.ts`)
- 크기 상한 + TTL + LRU 캐시를 직접 구현했다. `Map`이 삽입 순서를 유지하는 성질을 이용해, 조회할 때 항목을 맨 뒤로 다시 넣고 넘치면 맨 앞부터 버린다. 50줄 남짓이라 의존성을 늘리지 않았다.
- `getOrLoad`로 진행 중인 로딩을 공유한다(singleflight). 실패한 로딩은 캐시에 남기지 않는다.
- 목록 500개, 검색어 200개(목록과 분리), 날짜 추천 300개로 상한을 뒀다. 목록 항목 하나가 장소 최대 40개(수십 KB)라 상한으로 메모리를 묶는다.
- 검색어는 100자를 넘으면 외부 API를 부르기 전에 400으로 거절한다.

**검증**
같은 역 목록 요청 10개를 동시에 보내도 외부 검색 호출 수가 요청 1건분과 같고, 10개 응답이 같은 결과를 공유한다.

### 2-5. 장소 목록 직후 상세 조회 404 (R-9)

**문제**
장소 저장을 응답 뒤 백그라운드로 하므로, 목록을 받자마자 상세를 누르면 저장보다 조회가 먼저 도착해 404가 날 수 있었다.
백그라운드 저장이 실패하면 그 장소의 상세는 계속 404였다.

**방법**
최근 응답에 내보낸 장소를 placeKey로 기억해 둔다(최대 5,000개, 목록 캐시와 같은 TTL, 같은 객체 참조라 추가 메모리는 작다).
상세 조회에서 DB에 없으면 이 장소로 그 자리에서 upsert한 뒤 다시 읽는다. upsert라 백그라운드 저장과 겹쳐도 안전하다.
"목록 응답에 상세 필드를 포함"하는 대안은 응답 크기와 프론트 변경이 따라와 택하지 않았다.

**검증**
백그라운드 저장이 끝나지 않은 상태를 만든 뒤 상세를 조회해 200과 upsert 호출을 확인했다. 응답한 적 없는 장소는 여전히 404다.

### 2-6. 날짜 추천이 같은 달 첫 요청 날짜의 결과를 재사용 (N-3, 추가 발견)

**문제**
날짜 추천 결과를 `역 + 연-월`로 캐시했다. 그런데 후보 검색어(`9월 20일 성수 팝업`), 블로그 근거의 날짜 매칭,
점수(정확한 날짜·주말 가산점), 대체 검색어(주말)가 모두 **날짜**에 따라 달라진다.
같은 달의 다른 날짜 요청에는 첫 요청 날짜 기준으로 고른 추천이 나갔다.
"선택한 날짜의 팝업을 우선 추천"이라는 핵심 기능이 역·월마다 첫 요청에서만 제대로 동작한 셈이다.

**방법**
- 추천 캐시 키를 정확한 날짜로 바꿨다.
- 줄어드는 적중률은 네이버 클라이언트에 **검색어 단위 캐시**를 둬서 보완했다(지역 검색 2시간, 블로그 검색 30분).
  `2026년 9월 성수 팝업스토어` 같은 월 단위 검색어는 날짜가 달라도 같은 문자열이라 그대로 재사용되고,
  날짜가 들어간 검색어만 새로 호출된다. 목록 API와 추천 API가 같은 검색어를 쓸 때도 공유된다.

**검증**
9월 19일 추천 후 9월 23일을 요청하면 `9월 23일`이 들어간 검색어로 다시 고르는지 확인했다(이전 코드는 캐시 적중으로 검색 자체를 하지 않아 실패하는 테스트).

## 3. 데이트 코스 협업

### 3-1. 공동 편집 lost update (R-7)

**문제**
`PATCH /date-courses/:id`의 `items`는 코스 아이템 **전체 목록**이고, 서버는 목록에 없는 기존 아이템을 지운다.
상대가 방금 추가한 아이템을 모른 채 보낸 요청은 그 아이템을 조용히 지운다.
날짜 수정과 아이템 수정이 트랜잭션으로 묶여 있지 않았고, 중복 장소 검사가 **삭제 뒤에** 있어서 검사가 실패해도 삭제는 남았다.

**방법과 이유**
- `date_courses.version` 컬럼(낙관적 락)을 추가했다. 요청에 `version`이 있으면
  `UPDATE date_courses SET …, version = version + 1 WHERE id = $1 AND version = $2` **한 문장**으로 확인과 증가를 동시에 한다.
  영향받은 행이 0이면 409(`다른 사람이 먼저 코스를 수정했습니다…`). 읽고 비교하고 쓰는 3단계로 나누면 그 사이에 다시 경쟁이 생긴다.
- 비관적 락(`SELECT … FOR UPDATE`)만으로는 lost update를 막지 못한다. 두 요청이 순서대로 실행될 뿐, 늦은 요청이 오래된 화면을 기준으로 덮어쓰는 것은 그대로이기 때문이다. 문제는 "동시 실행"이 아니라 "오래된 상태 기준의 쓰기"다.
- 코스 행을 먼저 갱신해 행 락을 잡은 **뒤** 현재 아이템을 읽고, 날짜·아이템 쓰기를 한 트랜잭션으로 묶었다. 검증(중복 장소 등)은 모두 끝낸 뒤 쓴다. 소켓 알림은 커밋 뒤에 보낸다.
- 응답에 `version`을 담는다. **`version`은 아직 선택 값이다.** 현재 프론트가 보내지 않으므로 필수로 만들면 배포 즉시 코스 수정이 깨진다. 프론트가 보내기 시작하면 필수로 바꾼다.
- 전체 목록 대신 "추가·삭제·순서 변경" 같은 연산 단위 API로 바꾸는 방안은 프론트·백엔드 계약을 다시 짜야 해서 이번 범위에서 제외했다.

**마이그레이션**
`src/database/migrations/1757763600000-add-date-course-version.ts`
- `ADD COLUMN IF NOT EXISTS "version" integer NOT NULL DEFAULT 1` — 기존 행은 1로 채워진다. synchronize로 이미 컬럼이 생긴 로컬 DB에서도 안전하다.
- 테이블이 없는 빈 DB(최초 synchronize 전)에서는 건너뛴다. TypeORM 1.0은 마이그레이션을 synchronize보다 먼저 실행하기 때문이다.

**검증**
- 단위 테스트: 버전 불일치 → 409 + 아이템 조회·삭제·저장·알림 없음, 중복 장소 → 삭제 전에 400, 응답에 버전 포함.
- 실제 DB: 마이그레이션이 기존 행을 1로 채우고, 두 번 실행해도 한 번만 기록되며, 빈 DB에서는 건너뜀.
- TypeORM이 만드는 SQL: `UPDATE "date_courses" SET "date" = $1, "version" = "version" + 1, "updated_at" = CURRENT_TIMESTAMP WHERE ("id" = $2 AND "version" = $3)`

### 3-2. 소켓 출처·토큰·방 정리 (R-8)

| 점검 내용 | 확인 결과 | 조치 |
|---|---|---|
| 소켓 CORS가 모든 출처 허용 | 문제 확인 | REST와 같은 허용 목록(`src/common/cors.ts`)을 쓰고, **WebSocket 업그레이드는 `allowRequest`에서 Origin을 직접 확인** |
| 쿼리스트링 토큰 허용 | 문제 확인 | 제거. handshake `auth.token`과 Authorization 헤더만 받는다(프론트는 `auth.token`만 사용) |
| 코스 삭제 후에도 방에 남음 | 문제 확인 | `course:deleted` 이벤트를 보내고 `socketsLeave`로 방을 비운다 |
| 토큰 만료와 무관하게 연결 유지 | 문제지만 **보류** | 아래 참고 |

- CORS만으로 부족한 이유: 브라우저는 WebSocket 연결에 CORS를 적용하지 않는다. engine.io 소스를 확인해 보니 업그레이드 요청에도 `cors` 미들웨어가 돌지만 헤더만 붙이고 거절하지 않는다.
  프론트가 `transports: ['websocket']`을 쓰므로 실제로 막으려면 `allowRequest`가 필요하다. 게이트웨이만 띄워 원시 WebSocket으로 확인한 결과, 허용 출처는 연결되고 다른 출처는 **400으로 거절**됐다.
- 출처 목록은 요청 시점에 읽는다. 게이트웨이 데코레이터는 모듈을 불러올 때 평가되므로 그때는 `.env`가 아직 로드되지 않았을 수 있다.
- 형식이 틀린 `courseId`는 uuid 컬럼 조회 전에 거절한다(N-4와 같은 이유).
- **토큰 만료 시 연결 끊기를 보류한 이유**: 현재 프론트는 연결할 때 토큰을 한 번 넣고 재연결에도 같은 토큰을 쓴다. 서버가 만료 시각에 끊으면 15분 뒤부터 실시간 반영이 조용히 멈춘다.
  또 소켓 이벤트는 "바뀌었다"는 알림(코스 ID, 수정자 ID)뿐이고, 실제 내용은 인증된 REST로 다시 받는다. 위험은 작고 회귀 비용은 크다고 판단했다.
  프론트가 `auth`를 콜백(`auth: (cb) => cb({ token: 최신 토큰 })`)으로 바꾼 뒤 서버에서 만료 시각에 끊도록 하는 것이 순서다.

### 3-3. 초대 링크 참여 인원 제한 (R-8)

**문제**
초대 링크는 14일 동안 여러 번 쓸 수 있고 PARTNER 수에 제한이 없어서, 링크가 퍼지면 모르는 사람이 코스를 보고 고칠 수 있었다.

**방법**
- 커플 서비스이므로 PARTNER는 한 명으로 제한한다. 이미 파트너가 있으면 다른 사람의 수락은 409다.
- 같은 사람이 링크를 다시 열면 참여 상태 그대로 코스를 돌려준다. 수락할 때 토큰을 지우는 "1회용"은 택하지 않았다. 이미 참여한 파트너가 링크를 다시 눌렀을 때 404가 나기 때문이다. 파트너 1명 제한만으로 "다른 사람은 들어올 수 없다"는 목적을 스키마 변경 없이 달성한다.
- 두 사람이 동시에 수락해도 한 명만 들어가도록 코스 행을 `SELECT … FOR UPDATE`로 잠근 채 확인하고 추가한다(생성 SQL `… LIMIT 1 FOR UPDATE` 확인).

## 4. 인증 (추가 발견)

### 4-1. 소셜 access token의 발급 대상 미검증 (N-6)

**문제**
구글·네이버 로그인은 프론트가 implicit flow로 받은 access token을 백엔드가 받아 프로필만 조회했다.
access token은 "누가 로그인했는가"만 알려 주고, "어느 앱을 위해 발급됐는가"는 따로 확인해야 한다.
이를 건너뛰면 다른 앱이 사용자에게서 받은 토큰을 그대로 넘겨 그 사용자로 로그인할 수 있다(토큰 치환).
카카오도 access token을 직접 받는 경로는 같다.

**방법**
- 구글: `tokeninfo`의 `aud`가 `GOOGLE_CLIENT_ID`(쉼표로 여러 개)인지 확인하고, userinfo의 `sub`와도 맞춘다. 두 호출은 병렬로 해서 지연을 늘리지 않았다.
- 카카오: access token을 직접 받은 경우에만 `access_token_info`의 `app_id`가 `KAKAO_APP_ID`인지 확인한다. code flow는 우리 키로 직접 교환한 토큰이라 확인이 필요 없다.
- 환경변수가 없으면 검증을 건너뛰고 시작할 때 경고를 남긴다. 배포 직후 로그인이 막히지 않게 하기 위한 전환 기간 처리다. **운영에 두 값을 설정해야 실제로 보호된다.**
- 네이버는 토큰이 어느 앱에 발급됐는지 확인할 API가 없다. 서버가 client secret으로 code를 직접 교환하는 방식으로 바꿔야 하며, 프론트 변경이 필요해 후속 과제로 남겼다.

### 4-2. 소셜 첫 로그인 동시 요청 (N-5)

**문제**
사용자 저장과 소셜 계정 저장이 트랜잭션으로 묶여 있지 않았다. 같은 계정의 첫 로그인이 동시에 오면(버튼 연타, 재시도)
둘 다 "계정 없음"을 보고 가입을 시도하고, 늦은 쪽은 유니크 제약에 걸린다.

**재현** (검증용 DB, 가짜 사용자, 두 요청이 모두 "계정 없음"을 보도록 맞춘 뒤 동시 실행)

| | 결과 | 사용자 행 |
|---|---|---|
| 수정 전 | 한 요청 `QueryFailedError`(=500) | **2개 (소셜 계정 없는 고아 1개)** |
| 수정 후 | 두 요청 모두 같은 사용자로 로그인 | 1개 |

**방법**
사용자와 소셜 계정을 한 트랜잭션에서 만들고, 유니크 위반(23505)이면 먼저 만들어진 사용자를 다시 읽어 로그인시킨다.

### 4-3. refresh token 동시 사용 (검토 후 보류)

같은 refresh token으로 동시에 들어온 요청은 둘 다 새 토큰을 받는다(읽고 확인하고 쓰는 사이에 경쟁).
조건부 UPDATE로 하나만 성공하게 만들 수 있지만, 현재 프론트의 `ensureFreshToken`은 갱신 요청을 하나로 모으지(single-flight) 않는다.
여러 API가 동시에 나가는 순간 두 번째 갱신이 401을 받고, 프론트는 401이면 로그인 정보를 지우므로 **사용자가 로그아웃된다.**
보안 이득(밀리초 단위 창의 중복 발급 차단)보다 회귀 비용이 크다고 판단했다.
프론트가 갱신을 하나로 모은 뒤, 서버에서 원자적 회전과 재사용 탐지(폐기된 토큰이 다시 오면 그 사용자의 토큰을 모두 폐기)를 함께 도입하는 것이 순서다.

## 5. 요청 검증 (N-4, 추가 발견)

**문제**
검증이 없는 값이 그대로 DB에 가서 DB 오류가 500으로 나갔다.
- 경로의 코스 ID가 UUID가 아니면 uuid 컬럼 조회에서 `invalid input syntax for type uuid`
- `GET /places/search?stationId=abc` → `Number('abc')` = NaN으로 조회
- 컬럼 길이(`varchar(120)` 등)를 넘는 문자열 → `value too long`
- 위도·경도에 숫자가 아닌 값 → `numeric` 컬럼에 NaN 저장 가능

**방법**
- `ParseUUIDPipe`(코스 ID), `ParseIntPipe({ optional: true })`(stationId)
- DTO 문자열 길이를 엔티티 컬럼 길이와 맞추고, 위경도 범위(`IsLatitude`/`IsLongitude`), 아이템 수(최대 20, 로그인 없이 부르는 도보 계산 API 포함), 수정 요청 아이템 ID의 UUID 형식을 검증한다.

**검증**
main.ts와 같은 전역 `ValidationPipe`로 컨트롤러를 띄워 400과 "서비스 미호출"을 확인했다.

## 6. 운영 설정 (R-10)

### 6-1. 스키마 자동 동기화

**문제**
`synchronize: NODE_ENV !== 'production'`이라 배포 환경에 `NODE_ENV` 설정이 빠지면 운영 DB에서 synchronize가 켜진다.
synchronize는 컬럼 이름만 바꿔도 기존 컬럼을 지우고 새로 만든다.

**방법**
- `DATABASE_SYNCHRONIZE=true`를 명시한 경우에만 켜고, production에서는 설정과 상관없이 끈다.
- 스키마 변경은 `src/database/migrations`에 SQL로 남기고 앱이 뜰 때 적용한다(`migrationsRun`).
  마이그레이션 목록은 glob 대신 클래스를 직접 나열한다. 빌드 결과에 생기는 `.d.ts`까지 glob이 잡아 실행하려다 실패하기 때문이다.
- 로컬에서 **빈 DB로 처음 시작할 때만** `DATABASE_SYNCHRONIZE=true`가 필요하다. 이미 테이블이 있는 DB는 마이그레이션만으로 충분하다.

### 6-2. 직접 구현한 JWT (R-10-2)
구현에는 `timingSafeEqual`, `alg`/`typ` 고정, `iss`/`aud`/`nbf`/`exp` 검증, 시크릿 길이 검사가 모두 있어 교체할 결함은 찾지 못했다.
라이브러리(`jose`)로 바꾸는 것은 동작 변화 없이 위험만 생겨 하지 않았다. 면접에서는 "학습 목적으로 직접 구현했고, 검증 항목은 이렇다"로 설명하면 된다.

### 6-3. 테스트가 시작 단계에서 멈춤 (R-10-3)
코드 문제가 아니라 로컬 환경 문제였다. 프로젝트가 iCloud로 동기화되는 `~/Documents` 아래에 있고 디스크 여유가 적어,
macOS가 `node_modules` 파일 약 2만 9천 개를 클라우드로 내려 둔 상태(dataless)였다. `require('typeorm')`이 이런 파일을 읽으며 다운로드를 기다리다 멈췄다.
의존성을 다시 설치하자 기존 테스트 38개가 정상 실행됐다. 프로젝트를 iCloud 밖으로 옮기거나 디스크 여유를 확보하면 재발하지 않는다.

## 7. 성능 테스트

### 7-1. 방법

- **대상**: 사용자 요청이 많은 API 세 가지
  - `GET /stations?region=SEOUL` — 앱에 들어올 때마다 호출된다(수도권 655개 역, 응답 155KB)
  - `POST /random/subway` — 핵심 기능. 후보가 가장 많은 **최악 조건**(1번 역 + 60분, 후보 552개)과 수도권 중앙값인 **보통 조건**(283번 역 + 40분, 후보 166개)
  - `GET /stations/:id/places` — 외부 API(네이버)를 부르는 API(7-4)
- **도구**: ApacheBench(`ab -k`), 동시 사용자 1/10/50/100명, 각 15초 x 3회의 중앙값. 측정 전 2,000건 워밍업.
  측정 중 앱 프로세스 CPU를 1초마다 기록했다. 스크립트는 `scripts/load-test/`에 있다.
- **조건**: `npm run build` 후 `NODE_ENV=production`으로 실행. 지하철 테이블만 복사한 별도 DB.
  부하 발생기와 서버가 같은 장비라 네트워크 지연은 빠져 있다.
- **병목 찾기**: 같은 부하를 걸고 `node --cpu-prof`로 CPU 프로파일을 떠 모듈·함수별 self time을 집계했다.
- **동일성 확인**: 바꾸기 전 응답을 저장해 두고 바꾼 뒤와 비교했다.
  - 역 목록: 4가지 요청(전체·수도권·부산·없는 지역) 모두 내용이 같음. 단, 환승역 70곳의 노선 **순서**가 달랐는데, 원래 쿼리에 노선 정렬이 없어 실행 계획에 따라 순서가 바뀌던 것이라 노선 ID 순으로 고정했다.
  - 역 추천: 모든 출발역 879개 x 20/40/60분 = 2,637개 조합에서 후보 집합(역, 이동시간)이 변경 전 조인 쿼리와 **모두 같음**.

### 7-2. 기준선과 병목

| 역 추천, 최악 조건 | 208 RPS | 533ms | 약 115% |

역 추천(최악 조건)의 CPU 프로파일:

| 비중 | 내용 |
|---|---|
| 56% | TypeORM 엔티티 변환(`RawSqlResultsToEntityTransformer`): 후보 552개 역을 역·노선과 조인한 행 수백 개를 객체로 조립 |
| 16% | pg가 그 행들의 문자열 컬럼을 디코딩(`Buffer.toString`) |

요청마다 후보 전부를 메타데이터와 함께 엔티티로 만든 뒤 **하나만** 골라 응답하고 있었다.

### 7-3. 개선

**P-1. 역 메타데이터 카탈로그** (`src/stations/station-catalog.service.ts`)
- 역·노선 데이터는 데이터 반영(이동시간 캐시 재생성과 함께) 때만 바뀐다. 한 번 읽어 응답 형태로 만들어 메모리에 두고 공유한다.
  같은 프로세스에서 재생성하면 즉시 무효화하고, CLI나 DB 직접 수정은 TTL(10분)로 반영한다.
- 역 추천은 DB에서 `(도착역 ID, 이동시간)` 정수 두 개만 `(출발역, 이동시간)` 인덱스로 읽고, 지역 필터·가중치 계산·응답 구성은 카탈로그로 한다.
- 역 목록은 요청마다 조인하지 않고 카탈로그의 응답 배열을 돌려준다.

**P-2. 역 목록 응답 사전 직렬화·압축** (`src/common/http/precompressed-json.ts`)
- P-1 뒤 역 목록의 CPU는 JSON 직렬화 38%, 문자열→버퍼 인코딩 33%, ETag 해시 10%였다. 내용이 바뀌지 않는 155KB를 요청마다 다시 만들고 있었다.
- 카탈로그가 바뀔 때 직렬화된 버퍼, gzip·brotli 압축본, ETag를 한 번 만들어(압축은 스레드 풀에서) 재사용한다.
  `Accept-Encoding`에 맞춰 고르고, `If-None-Match`가 같으면 304, `Cache-Control: public, max-age=300`.
- 없는 지역 코드는 모두 빈 응답 하나를 함께 써서, 입력값 종류만큼 응답이 쌓이지 않게 했다.
- 압축을 요청마다 하는 `compression` 미들웨어 대신 미리 압축한 이유: 응답이 고정돼 있어 매번 압축할 이유가 없고, 의존성도 늘지 않는다.

**P-3. 운영 로그 레벨** (`src/common/log-levels.ts`)
- Nest는 운영에서도 기본으로 debug까지 남긴다. 변경 전에는 역 추천 1건마다 로그 3줄과 후보 목록(약 5.4KB)이 남아,
  부하 테스트 동안 **13만 7천 건에 767MB**가 쌓였다.
- `LOG_LEVEL`(최소 레벨)을 두고 운영 기본값을 `log`로 했다. 장소 추천의 점수 진단 로그 4개는 debug로 내리고, debug가 꺼져 있으면 JSON을 만들지도 않는다.

**장소 목록 — 외부 API 동시 사용자 시나리오** (네이버 스텁, 응답 60~150ms)

| 시나리오 | 변경 전(`60c480a`) | 변경 후 |
|---|---|---|
| 1명, 처음 조회하는 역 | 1,979ms | **1,119ms (-43%)** |
| 같은 역에 동시 10명 | 외부 호출 140회, p95 11,361ms | **외부 호출 14회, p95 1,201ms** |
| 서로 다른 역 5명 (p50 / p95) | 5,395 / 5,737ms | 5,279 / 5,681ms |
| 서로 다른 역 10명 (p50 / p95) | 10,542 / 11,310ms | 10,443 / 11,224ms |
| 캐시 적중 10명 (p95) | 32ms | 34ms |

- 1명일 때 빨라진 것은 묶음 사이 150ms 대기 제거와 간격 계산 오류 수정(2-1, 2-2), 같은 역 동시 요청은 singleflight(2-4) 효과다.
- **서로 다른 역에 동시 사용자가 늘면 전후가 같다.** 네이버 지역 검색은 한 번에 5건까지만 주기 때문에 목록 1건에 검색어 14개가 필요하고,
  전역 호출 간격(80ms, 초당 약 12.5회)이 상한이라 대기 시간이 사용자 수에 비례한다(10명 x 14회 / 12.5회 ≈ 11초). 코드로 줄일 수 있는 부분이 아니다.
  - 요청마다 검색어를 한꺼번에 대기열에 넣으면(완전 FIFO) 목록 요청들의 중앙값은 절반으로 줄지만, 뒤에 온 짧은 요청(키워드 검색 1회)이 앞의 대기열 전체(최대 11초)를 기다리게 된다.
    요청당 동시 4개 창은 짧은 요청을 보호하는 쪽을 택한 설계라 유지했다.
  - 줄이려면 요청당 검색어 수를 줄이거나(추천 품질과 맞바꿈), 인기 역(가중치 A·B)을 미리 채우거나, 캐시 만료 시 이전 값을 주며 뒤에서 갱신(stale-while-revalidate)해야 한다(9장).
- 최대 동시 외부 호출은 2(스텁 응답이 호출 간격보다 짧아 4까지 차지 않음), 1초당 최대 13회로 스케줄러 상한 안이었다.

| `LOG_LEVEL` | 비워 두면 운영은 `log` 이상만 남긴다. 조사할 때만 `debug`로 잠시 켠다 |
| 마이그레이션 | 배포 후 첫 시작 때 `date_courses.version`이 자동으로 추가된다(기존 행은 1) |
| 로그 점검 (R-1) | 그동안 열려 있던 재생성 API가 의도치 않게 호출됐는지 운영 로그에서 `이동시간 캐시 재생성 시작`을 검색한다 |

## 9. 후속 과제

1~4는 프론트 변경이 먼저 필요하다.

1. 코스 수정 시 `version`을 보내고 409를 받으면 최신 상태를 다시 불러와 사용자에게 알린다 → 이후 서버에서 `version` 필수화
2. 토큰 갱신(single-flight) 단일화 → 이후 서버에서 refresh token 원자적 회전 + 재사용 탐지
3. 소켓 `auth`를 콜백으로 바꿔 재연결 때 최신 토큰을 쓰게 한다 → 이후 서버에서 토큰 만료 시 연결 종료
4. 네이버 로그인을 서버 측 code 교환으로 전환 → 토큰 발급 대상 보장
5. 장소 목록 캐시가 만료될 때 이전 값을 주면서 뒤에서 갱신(stale-while-revalidate). 인기 역 사용자가 만료 직후 첫 요청에서 1초 넘게 기다리지 않게 한다(7-4).
6. (선택) 공개 API(장소 검색)에 IP 단위 요청 제한. 외부 API 하루 한도를 한 클라이언트가 소진할 수 있다.
   다만 배포 환경의 프록시 단계 수를 확인해 `trust proxy`를 정확히 설정해야 해서(잘못 설정하면 모든 사용자가 한 IP로 묶임) 이번에는 하지 않았다.
